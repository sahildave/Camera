# DuoCam fork delta

This fork adds three small camera seams for DuoCam, plus one fix to inherited upstream behaviour:

- `CameraRearLens` selects the exact rear `AVCaptureDevice.DeviceType` for ultra-wide, wide, or telephoto cameras. `CameraManager.selectRearLens(_:completion:)` and the matching `MCamera.Controller` method report a `Result` exactly once after the serialized input swap succeeds or fails. Unsupported lenses are never replaced with another lens.
- `CameraFrame` and `CameraFrameObserver` expose live frames from the library's existing `AVCaptureVideoDataOutput`. Register with `CameraManager.setFrameObserver(_:queue:)` or the matching controller method. Registration is weak, replaces the previous observer atomically on the capture/session queue, and callback delivery is serial on a queue targeted at the caller-supplied queue while capture delivery is active.

- `CameraManager.setFocusAndExposure(at:focusMode:exposureMode:completion:)` and the matching `MCamera.Controller` method set the focus and exposure point of interest from a normalised point in the preview's coordinate space (`(0, 0)` is the preview's top-left corner; out-of-range values are clamped). The device lock/configure/unlock is serialized on the capture/session queue and the `Result` is reported exactly once. Continuous vs. locked behaviour is expressed with the AVFoundation `FocusMode`/`ExposureMode` enums, defaulting to the one-shot `.autoFocus`/`.autoExpose` pair; a mode or point of interest the active device does not support fails explicitly rather than being silently ignored. Focus and exposure are requested independently: each mode is optional, and a nil mode leaves that half of the device untouched, so a device that supports only one of the two points of interest is served by asking for only that half instead of failing wholesale. Every requested half is checked before anything is applied, so `.success` means every requested half was applied and a failure leaves the device unchanged. The capture queue owns the active video input — recorded when setup adds it or adopts one already in the session, and updated by every swap — so neither the lens nor the tap-to-focus path blocks the main actor to push it back down.

The library owns each `CMSampleBuffer`; it is valid only for the duration of the observer callback. Consumers that work asynchronously must copy the data they need before returning. Frame delivery does no encoding or Vision work.

## Photo capture

The photo path is a fork default, not a knob: the fork opts every capture into the full-quality path rather than exposing capture-settings control. `AVCapturePhotoOutput.maxPhotoQualityPrioritization` is set to `.quality` when the output is added, `maxPhotoDimensions` is raised to the largest of the active format's `supportedMaxPhotoDimensions` (iOS 16+), and per-capture settings mirror the output's own values, so a per-capture request can never exceed the output maximum. The ceiling is recomputed on every active video input change — not only at setup — because flipping the camera position or selecting a rear lens activates a different format whose maximum the previous format's value may exceed; `CameraManager.resetAttributes(device:)` is the single point every input swap already funnels through, so the recomputation hangs off it. Consumers get full-sensor, `.quality`-tier stills by default and cannot lower that from the public API.

`MCameraMedia.getOriginalPhotoData()` returns the unmodified `fileDataRepresentation()` bytes of a captured photo — container, EXIF and any auxiliary depth or matte data intact — alongside the decoded, filtered `UIImage` that `getImage()` already returned. The decoded image is unchanged, so previews and filters keep working and the consumer chooses which representation it needs.

`MCameraScreen.capturedPhotoData` reads those bytes off the manager — `cameraManager.attributes.capturedMedia?.getOriginalPhotoData()` — mirroring how `MCameraScreen.photoCaptureError` reads the failure. It exists because a custom camera screen is otherwise the one place that cannot reach the capture: `imageCapturedAction` hands over a bare `UIImage`, `MCamera.Controller` exposes only the `MCamera` itself, and `CameraManager.attributes` is internal to the library, so the only public holder of `MCameraMedia` is `MCapturedMediaScreen`. Installing one is not an acceptable route: `MCamera.createContent()` swaps the camera screen for the captured-media screen whenever `capturedMedia` is non-nil, and `createCameraScreen()` carries `.onAppear -> manager.setup()` / `.onDisappear -> manager.cancel()`, so every shutter press would tear down and rebuild the capture session and the frame observer. Reading the attribute from the camera screen that is already installed costs nothing and changes no lifecycle. `attributes.capturedMedia` is set before the capture is announced — `setCapturedMedia(_:)` publishes it and the `onChange` that fires `imageCapturedAction` is driven by that same publish — and it stays set until `MCamera.Controller.reopenCameraScreen()` clears it, so the accessor is readable for the whole window in which a consumer would want it.

Photo capture failures are observable instead of silent. `MCameraError` gains `photoCaptureSessionNotReady`, `photoCaptureFailed` (the `AVCapturePhotoOutput` delegate reported an error) and `photoPostProcessingFailed` (no data representation, or the image could not be decoded). They are published on the manager as `CameraManager.photoCaptureError` and read back through `MCameraScreen.photoCaptureError`, mirroring how a successful capture is delivered on the published `capturedMedia` attribute; the error clears at the start of every shutter press — before the readiness check, so the clear happens even on the path that fails immediately — and again when media is delivered, so a repeated identical failure is published as a change rather than being swallowed by equality. The clear and the new failure are two publishes on the same main-actor turn, so a consumer that only samples the latest state per SwiftUI update still sees one value; a consumer that must count presses should key its own state off the press, not off this attribute. The terminal `attributes.error` path is deliberately not reused here: it swaps `MCamera` to its error screen for good, which is right for a permissions failure but would tear the camera down over a single retryable shutter press.

## Test seams

The delta widens a few internal surfaces so the behaviour above can be tested without a physical device. All of them stay internal to the library; none is public:

- `CaptureDevice` gains `isFocusModeSupported(_:)` and `deviceType`, mirroring the existing `isExposureModeSupported(_:)`, so the focus-mode gate is expressed against the protocol instead of a concrete `AVCaptureDevice`. The protocol itself is now `Sendable`, because devices are configured on the capture/session queue.
- `MockCaptureDevice` converts `isFocusPointOfInterestSupported` and `isExposurePointOfInterestSupported` from computed constants to stored properties and adds `supportedFocusModes`/`supportedExposureModes` and `deviceType`, so a test can model a device that supports only one point of interest or only some modes. `MockDeviceInput` gains `supportedRearDeviceTypes` for the same reason on the lens path.
- `CameraManager.captureQueue` is internal rather than private, so a test can drive an input swap directly and assert what setup does with a session that was already populated. `CameraManagerPhotoOutput.getPhotoOutputSettings()` and `processCapturedPhoto(imageData:error:)` are internal rather than private, so a test can assert the capture settings and drive photo post-processing without an `AVCapturePhotoOutput` delegate callback. `configureFullQualityCapture(for:)` is internal for the same reason, and records `fullQualityCaptureDeviceID` — the device the current ceiling was computed from — because the dimensions themselves can only be read off a real `AVCaptureDevice`. Everything else in that file stays private.

## Inherited bug fix

The accelerometer path reconfigured the frame-output connection on every device-orientation change, even when the camera was locked to portrait, so a consumer tapping raw frames saw the delivered sample buffer flip between portrait and landscape mid-session. `CameraManager.frameOutputOrientation` now resolves to `.portrait` while `orientationLocked` is set, pinning every caller of `configureFrameOutputConnection()`, and the motion manager no longer reconfigures the connection when locked — matching the existing `redrawGrid()`/`updateFrameOrientation()` gating. `attributes.deviceOrientation` keeps tracking the accelerometer, because the photo and video paths and the public `deviceOrientation` accessor consume it and only the frame output is meant to be pinned.

`setup()` suspends on the permission request before it touches the session, so a caller that replays state onto the manager from a SwiftUI `onAppear` — selecting a rear lens, say — reaches the still-empty session first and fills its single video-input slot. `setupDeviceInputs()` then failed `canAddInput` and threw `.cannotSetupInput`, aborting setup before `setupDeviceOutput()` ran. The `AVCapturePhotoOutput` was never added to any session, so it had no connection and no `activeFormat`, and the next `configureFullQualityCapture` raised an uncatchable Objective-C exception from `setMaxPhotoDimensions`. Three changes close it:

- `adoptOrAddVideoInput(_:)` keeps whichever video input the session already carries instead of adding a second and throwing, so the lens the caller picked survives and setup runs to completion. Membership is tracked on the capture queue rather than derived from `session.deviceInputs`, whose `AVCaptureSession` implementation is an all-or-nothing array cast that yields `[]` if any input does not conform.
- Everything setup configures afterwards reads the device back off the session via `activeVideoInputDevice` rather than resolving it by camera position. `getCameraInput()` only knows front and back, so after an adoption it would name the default wide-angle device while the session ran a telephoto — computing the full-quality ceiling, and locking and configuring the device in `startSession()`, against a camera that was not capturing.
- `configureFullQualityCapture(for:)` skips `maxPhotoDimensions` unless the output already has a video connection, so a future ordering bug degrades the capture ceiling instead of raising an exception no Swift caller can catch.

`setResolution` now applies the preset through the capture queue instead of opening a `beginConfiguration`/`commitConfiguration` transaction on whichever thread called it, which for the main-actor replay path could overlap a transaction the queue was already running for an input swap. `setupCameraLayer()` still writes `sessionPreset` off-queue on the initial-setup path; it runs before any input is added, and is left alone here.

The implementation keeps one capture session and one video-data output, and continues to support the existing front/back camera API. This bounded delta is intended for upstream contribution as a focused API and test seam.
